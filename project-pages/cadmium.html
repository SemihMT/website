Overview

Cadmium is a cross-platform game engine I'm building from scratch in C++, targeting both native desktop and the browser via WebAssembly. The goal is to have a self-contained environment where developers can write, run, and iterate on games entirely in the browser without having to install anything on their end.

The project is driven by curiosity more than necessity. I wanted to understand what actually happens inside an engine and how I could replicate the systems that power successful engines like Unity, Godot and Unreal. I wanted to learn how you make something that runs identically on Windows and in a browser tab. Building it myself is the only way to find out.

Cadmium is not finished. It's an active work in progress and this page reflects where it currently is, not where I want it to be.

The latest version of Cadmium is hosted on Github Pages using a CI/CD pipline. For ease of access, the canvas on that page is also rendered here using an iframe.

Technical Highlights

(as of 04/2026)

Native and WebAssembly in harmony

The build system uses CMakePresets to switch cleanly between native Clang builds and Emscripten without touching the source. The game loop abstraction handles the fundamental difference between the two targets: native uses a while loop and Emscripten uses emscripten_set_main_loop. The logic is hidden behind a single Engine::Run() call.

Application interface

Users interact with the engine through a simple Application base class with lifecycle hooks: OnStart, OnUpdate, OnFixedUpdate, OnRender, OnEvent, and OnShutdown. Only OnRender is required.

Fixed timestep with variable rendering

Physics and game logic run at a fixed 60Hz via an accumulator pattern, decoupled from the render rate. OnFixedUpdate fires at consistent intervals regardless of frame time, while OnUpdate and OnRender run as fast as the hardware allows or at the requested frequency by using the SetTargetFPS() function.

ImGui as an optional compile-time feature

ImGui support is gated behind a CADMIUM_IMGUI CMake option. When enabled, the engine initializes and drives the ImGui frame lifecycle automatically, and exposes an OnImGuiRender hook on the Application. When disabled, ImGui is stripped entirely from the build. This way people can write debug UI to their heart's content and have it be removed completely without manual work.

Dependency management via FetchContent

All external dependencies (SDL3, ImGui, Catch2,...) are pulled at configure time via CMake's FetchContent with pinned release tags. A shared cache directory prevents redundant downloads across clean builds. This keeps things easy in my opinion, no manual setup on a new machine beyond having CMake, Ninja, and a compiler. You do need an internet connection though, which is a con.

Architecture

The project is split into three CMake targets:

  1. cadmium-engine is a static library that knows nothing about games. It owns the window, the renderer, the loop, and the platform abstractions.
  2. cadmium-sandbox is an executable that links against the engine and implements the Application interface. It's essentially where I make my demo apps.
  3. cadmium-editoris a WIP target, currently a placeholder, that will eventually host the ImGui-based editor with its own asset browser and code editor.

The include and source directories are separated — engine/include/cadmium/ is the public API surface, engine/src/ is implementation detail. Consumers include <cadmium/core/Engine.hpp> and see nothing they don't need to.

Minimal application example

+ 
#include <cadmium/core/engine.hpp>
#include <cadmium/core/application.hpp>

class MyGame : public Cadmium::Application {
public:
    void OnRender(SDL_Renderer* renderer) override {
        // draw here
    }

    void OnEvent(SDL_Event& event) override {
        if (event.type == SDL_EVENT_KEY_DOWN)
            if (event.key.key == SDLK_ESCAPE)
                Quit();
    }
};

int main() {
    Cadmium::Engine engine(
        std::make_unique<MyGame>(),
        "My Game", 1280, 720
    );
    engine.SetTargetFPS(60);
    engine.Run();
}
Roadmap

Each milestone builds directly on the previous one. No renderer abstraction before there's something worth abstracting and no scripting API before there are objects to script.

✓
Window and game loop
SDL3 window, fixed timestep accumulator, native and Emscripten targets building cleanly.
✓
ImGui integration
ImGui wired up as an optional compile-time feature with a dedicated OnImGuiRender hook.
→
GameObject and component model
Cache-friendly ECS-style architecture.
○
Lua scripting via Sol3
Embedded Lua interpreter with a clean C++ binding layer. Defines the API available to engine users.
○
Renderer abstraction
Backend-agnostic graphics layer. SDL_Renderer first, with a path to Vulkan, OpenGL and WebGPU.
○
Project export/import
Exporting Cadmium projects in a custom file format to enable sharing.
Why Build This

Most commercial engines are a black box with some documentation. They're monoliths, built incrementally across decades which makes grasping them completely an almost impossible task. As someone who is interested in how and why things work, I want to replicate the systems I see powering millions of games every day as an exercise.

Cadmium forces me to think about design, to plan ahead. I have to make sure I don't shoot myself in the foot, and when I eventually do, I need to fix it myself.

Cadmium also forces me to learn about the details that are so often overlooked. The combination of web and native support challenges my assumptions of what should work and how I need to approach programming. Learning and adapting to new platforms is maybe the biggest challenge of this project.

The long-term vision is a browser-based editor where someone can open a tab, write Lua, and have a running game in under a minute. Whether that's ambitious or naive probably depends on how the next few milestones go.
